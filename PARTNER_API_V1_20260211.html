Overview

The Partner API provides programmatic access to Goldbelly data for authorized partners. This RESTful API uses JSON for request and response payloads and requires authentication via Bearer tokens.

Base URL: https://api.goldbelly.com/partner_api/v1

Authentication: Bearer token authentication via the Authorization header

Response Format: JSON

Authentication

All API requests must include a valid API credential in the Authorization header using the Bearer authentication scheme.

Request Header Format

Authorization: Bearer YOUR_API_KEY_HERE

API Credential Requirements

  • API keys are 32-character alphanumeric strings
  • Each request logs usage by updating the credential's last_used_at timestamp
  • API credentials are tied to a partner entity (polymorphic association)

Authentication Errors

401 Unauthorized - Returned when:

  • No Authorization header is provided
  • Invalid or expired API key
  • Malformed authentication header (not using Bearer scheme)

Endpoints

GET /gift_cards/{code}
Gift Card Lookup

Retrieve gift card information by code, with verification via email or phone number.

URL Parameters

Parameter Type Required Description
code string Yes Gift card code (case-insensitive)

Query Parameters

Parameter Type Required Description
email string No* Email address associated with the gift card (case-insensitive)
phone_number string No* Phone number associated with the gift card (normalized to E.164 format)
* At least one of email or phone_number must be provided

Lookup Logic

E-Gift Cards:

  • Matches against recipient_email, sender_email, or recipient_phone_number
  • Requires either email OR phone_number parameter

Physical Gift Cards:

  • Matches against recipient_email or order purchaser_email
  • Requires email parameter (phone lookup not supported)

Gift Card Eligibility

Only returns gift cards that are:

  • Activated
  • Goldbelly-branded (not merchant-specific)
  • Match the provided verification credentials

Success Response

200 OK

{
  "available_cents": 7500,
  "code": "abc123xyz",
  "description": "Gift card for delicious treats",
  "used_cents": 2500,
  "value_in_cents": 10000
}

Response Fields

Field Type Description
available_cents integer Remaining balance in cents (derived from balance_in_cents)
code string Gift card code
description string/null Optional gift card description
used_cents integer Amount already redeemed in cents (derived from redeemed_value_in_cents)
value_in_cents integer Original gift card value in cents

Error Responses

404 Not Found - Returned when:

  • No code parameter provided
  • Gift card code doesn't exist
  • Gift card exists but email/phone doesn't match any associated records
  • Gift card is not activated or not Goldbelly-branded
{
  "code": "404",
  "errors": null,
  "message": "Entity could not be found",
  "status": 404
}

Example Requests

E-Gift Lookup by Email:

curl -X GET "https://api.goldbelly.com/partner_api/v1/gift_cards/ABC123XYZ?email=customer@example.com" \
  -H "Authorization: Bearer YOUR_API_KEY"

E-Gift Lookup by Phone:

curl -X GET "https://api.goldbelly.com/partner_api/v1/gift_cards/ABC123XYZ?phone_number=3078558012" \
  -H "Authorization: Bearer YOUR_API_KEY"
GET /orders/tracking
Order Tracking

Retrieve shipping and tracking information for completed order packages.

Query Parameters

Parameter Type Required Description
order_id integer Yes Goldbelly order ID
email string Yes Purchaser email address (case-insensitive)

Lookup Logic

  • Finds orders by exact ID match
  • Verifies ownership via case-insensitive email match against purchaser_email
  • Only returns completed orders
  • Filters to completed suborders that are not canceled

Success Response

200 OK

Returns an array of tracking information objects, one per completed suborder (package).

[
  {
    "carrier": "ups",
    "delivery_address": "123 Main St, Apt 4B, New York, NY, 10001",
    "delivery_date": "2024-01-17",
    "merchant_name": "Joe's Stone Crab",
    "order_id": 12345678,
    "product_names": "Original PieCaken",
    "product_urls": [
      "https://www.goldbelly.com/joes-stone-crab/original-piecaken"
    ],
    "recipient_name": "Jane Doe",
    "ship_date": "2024-01-15",
    "status": "in_transit",
    "total_in_cents": 9999,
    "tracking_number": "1Z999AA1234567890",
    "tracking_url": "https://www.ups.com/track?tracknum=1Z999AA1234567890"
  }
]

Response Fields

Field Type Description
carrier string/null Shipping carrier (e.g., "ups", "fedex") from current shipping label
delivery_address string Comma-separated delivery address (street1, street2, city, state, postal code)
delivery_date string/null ISO 8601 date string of requested delivery date
merchant_name string Name(s) of merchant(s) fulfilling the suborder
order_id integer Goldbelly order ID
product_names string Comma-separated product names, truncated to 40 characters
product_urls array of strings URLs to the product pages on Goldbelly
recipient_name string Full name of the delivery recipient
ship_date string/null ISO 8601 date string of scheduled ship date
status string Current tracking status or "unknown" if unavailable
total_in_cents integer Suborder total including taxes, in cents
tracking_number string/null Carrier tracking number
tracking_url string/null Full URL to carrier tracking page

Status Values

The status field reflects the current state from the shipping label tracking system. Common values include:

  • shipped
  • in_transit
  • out_for_delivery
  • delivered
  • unknown (when no tracking data is available)

Error Responses

404 Not Found - Returned when:

  • Order ID doesn't exist
  • Email doesn't match the order's purchaser email
  • Order exists but has no completed, non-canceled suborders
{
  "code": "404",
  "errors": null,
  "message": "Entity could not be found",
  "status": 404
}

Example Request

curl -X GET "https://api.goldbelly.com/partner_api/v1/orders/tracking?order_id=12345678&email=customer@example.com" \
  -H "Authorization: Bearer YOUR_API_KEY"
POST /orders/{id}/cancel
Order Cancellation

Cancel a completed order. The order must still be in a cancellable state.

URL Parameters

Parameter Type Required Description
id integer Yes Goldbelly order ID

Request Body Parameters

Parameter Type Required Description
email string Yes Purchaser email address (case-insensitive)

Lookup & Cancellation Logic

  • Finds the order by exact ID match
  • Verifies ownership via case-insensitive email match against purchaser_email
  • Only operates on completed orders
  • Validates the order is still in a cancellable state before proceeding
  • Processes a full cancellation with refund

Success Response

204 No Content

Returns an empty response body on successful cancellation.

Error Responses

404 Not Found - Returned when:

  • Order ID doesn't exist
  • Email doesn't match the order's purchaser email
  • Order is not in a completed state
{
  "code": "404",
  "errors": null,
  "message": "Entity could not be found",
  "status": 404
}

422 Unprocessable Entity - Returned when:

  • The order is not in a cancellable state (e.g., already shipped or delivered)
  • The cancellation service encounters an error during processing
{
  "code": "422",
  "errors": null,
  "message": "Something went wrong trying to cancel the order #12345678",
  "status": 422
}

Example Request

curl -X POST "https://api.goldbelly.com/partner_api/v1/orders/12345678/cancel" \
  -H "Authorization: Bearer YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"email": "customer@example.com"}'
POST /orders/resend_confirmation
Resend Confirmation Emails

Re-trigger order confirmation emails for a customer. Can target a specific order or all recent orders for a given email address.

Request Body Parameters

Parameter Type Required Description
email string Yes Purchaser email address (case-insensitive)
order_id integer No Specific Goldbelly order ID. If omitted, targets all recent orders for the email.

Lookup Logic

  • With order_id: Finds the specific completed order by ID and verifies the email matches purchaser_email
  • Without order_id: Finds all completed orders for the email within the last 7 days
  • Maximum of 5 orders can be processed per request

Processing Details

  • Clears any email hard bounces for the customer before resending
  • Re-triggers the order confirmation email for each matched order
  • Reports per-order success/failure in the response

Success Response

200 OK

{
  "emails_failed": 0,
  "emails_sent": 2,
  "orders_found": 2,
  "results": [
    {
      "product": "Original PieCaken",
      "email_sent": true
    },
    {
      "product": "Chicago Deep Dish Pizza",
      "email_sent": true
    }
  ],
  "time_window_days": 7
}

Response Fields

Field Type Description
emails_failed integer Number of orders where the confirmation email failed to send
emails_sent integer Number of orders where the confirmation email was successfully queued
orders_found integer Total number of matching orders found
results array Per-order results
results[].product string Primary product name for the order
results[].email_sent boolean Whether the confirmation email was successfully queued
time_window_days integer The lookback window in days used when searching by email only (currently 7)

Error Responses

404 Not Found - Returned when:

  • No completed orders found for the given email (within the 7-day window)
  • Specified order_id doesn't exist or email doesn't match
{
  "code": "404",
  "errors": null,
  "message": "Entity could not be found",
  "status": 404
}

422 Unprocessable Entity - Returned when:

  • Total matching orders exceeds the limit of 5
{
  "code": "422",
  "errors": null,
  "message": "Orders total (6) exceeds limit (5)",
  "status": 422
}

Example Requests

Resend for a specific order:

curl -X POST "https://api.goldbelly.com/partner_api/v1/orders/resend_confirmation" \
  -H "Authorization: Bearer YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"email": "customer@example.com", "order_id": 12345678}'

Resend for all recent orders:

curl -X POST "https://api.goldbelly.com/partner_api/v1/orders/resend_confirmation" \
  -H "Authorization: Bearer YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"email": "customer@example.com"}'

Error Handling

The API uses standard HTTP status codes and returns consistent error response structures.

Error Response Format

{
  "code": "404",
  "errors": null,
  "message": "Entity could not be found",
  "status": 404
}

Error Response Fields

Field Type Description
code string HTTP status code as string
errors object/null Validation errors object (key-value pairs of field errors)
message string Human-readable error message
status integer HTTP status code
help_url string/null Optional URL to documentation or help resources

HTTP Status Codes

Code Description Common Causes
200 OK Request succeeded
204 No Content Request succeeded with no response body (e.g., order cancellation)
400 Bad Request Missing required parameters, unpermitted parameters
401 Unauthorized Missing, invalid, or expired API credentials
404 Not Found Resource doesn't exist or verification failed
422 Unprocessable Entity Validation errors, duplicate records

Common Error Scenarios

Missing Authentication

{
  "code": "401",
  "errors": null,
  "message": "Unauthorized",
  "status": 401
}

Parameter Validation Errors

{
  "code": "400",
  "errors": null,
  "message": "param is missing or the value is empty: email",
  "status": 400
}

Rate Limiting & Best Practices

Usage Logging

  • Every authenticated request logs usage by updating the API credential's last_used_at timestamp
  • This occurs even for failed requests (404, validation errors, etc.)
  • Monitor your credential's usage patterns via your partner dashboard

Best Practices

1. Case Sensitivity

  • Email addresses are normalized to lowercase
  • Gift card codes are normalized to lowercase
  • Always send case-insensitive queries

2. Phone Number Formatting

  • Phone numbers are normalized to E.164 format (+13078558012)
  • Submit numbers with or without country code - the API handles normalization
  • International numbers are supported

3. Error Handling

  • Always check HTTP status codes before parsing response body
  • Implement retry logic with exponential backoff for 5xx errors
  • Do not retry 4xx errors (client errors) without fixing the request

4. Security

  • Never expose API credentials in client-side code
  • Rotate credentials if compromised
  • Use HTTPS for all requests (enforced by default)

5. Data Privacy

  • Gift card and order lookups require PII verification (email/phone)
  • This ensures only authorized parties can access sensitive information
  • Never cache or store customer PII unnecessarily

API Versioning

This is version 1 of the Partner API (/partner_api/v1).

  • The API version is part of the URL path
  • Breaking changes will result in a new API version
  • Non-breaking changes (new optional fields, new endpoints) may be added to existing versions
  • Deprecated versions will be supported for a minimum of 6 months after deprecation notice
